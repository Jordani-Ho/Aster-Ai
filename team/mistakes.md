## E-001：禁止项与授权项互斥未二选一

**日期**：2026-10-04
**提出人**：发起人（本人在 C 板块启动指令的复盘中主动指出）
**记录人**：C 板块设计

### 原指令缺陷

C 板块启动指令的边界一节里，同时出现两条互斥的约束：

| 原文 | 冲突点 |
| :-- | :-- |
| 「不跑命令」 | 禁止执行任何命令 |
| 「不 commit」 | 隐含「可以 commit，只是本步不做」——而 commit **必须**经命令执行 |

两条并列时，执行者无法判定：是「任何情况下都不能跑命令」，还是「本步不跑，但允许 commit」。
若指令中另有「授权 commit」字样，则与「不跑命令」**直接矛盾**，执行者必须自行选择违背哪一条。

### 结论（发起人定）

**「禁命令」与「授权 commit」互斥，二选一。今后写指令不得同时出现。**

- 要授权 commit → 不得写「不跑命令」。
- 要禁止命令 → 不得写任何形式的 commit 授权。

### 推广：同类互斥对

写指令前检查，下列各组**只能选一个**：

| A | B | 说明 |
| :-- | :-- | :-- |
| 禁命令 / 不跑命令 | 授权 commit / 授权跑测试 / 授权安装依赖 | 「禁命令」是总闸，任何需要执行动作的授权都与它互斥 |
| 只读 | 落盘 / 新建文件 / 改写文件 | 「本次只读」与「产出文件」互斥，除非明确分阶段 |
| 不 commit | 授权 commit | 字面互斥 |
| 不写代码 | 授权修改 `.py` / `.ts` 源文件 | 源文件即代码 |

### 反面样板

> 「你不写代码，不跑命令，不 commit。…… 完成后授权 commit。」

### 正面样板（二选一）

> 「本次只读：不改任何文件，不跑命令，不 commit。回报即可。」

或

> 「本次可落盘 + 可 commit：写 `docs/xxx.md`，跑 `pytest` 验证，验证通过后 commit。」

或（**分阶段**，推荐用于大任务）

> 「第一步只读回报，不改文件、不跑命令。
> 第二步（等确认后）授权落盘 + 跑测试 + commit。」

### 对分阶段指令的补充要求

分阶段时，**每一步的边界必须单独写清**，不得用一句总边界覆盖全程。
否则第二步的授权会与第一步的禁令冲突，重演 E-001。

## E-002：授权文件改了口径，角色卡没跟着改

**日期**：2026-10-04
**发现人**：C 板块（设计 CTO）
**性质**：E-001 的**变体**——不是同一份文件内互斥，而是**两份文件之间**矛盾，且**都被标为"当前有效"**。

> **✅ 处置结果（2026-10-04）**：已上报发起人，**发起人裁定**：
>
> > 「**之前的边界是前任知衡的规定，现在的边界以现任知衡给你的指令为准。**」
>
> ⇒ **裁定原则：角色/边界类冲突，以「现任责任人的指令」为准，不以历史角色卡为准。**
> ⇒ 本条的**检查清单仍然有效**（用于防止下次再出现同类冲突），但**冲突时的仲裁规则已明确**。

### 现象

| 文件 | 内容 |
| :-- | :-- |
| `team/decisions/decision-log.md` **D-035** | 「前任 C 板块角色卡中的『只碰 `docs/phase3-*` 和 `team/`』『**不写代码、不跑命令、不 commit**』——**均属前任会话约束，现已失效**」 |
| `team/instructions/INSTR-2026-10-04-03` | 要 C 板块**写 `backend/` 代码 + 跑 pytest + 产 `migrations/*.sql`** |
| `team/roles/C板块设计.md` **L34–46** | 仍然写着：「按白皮书 v2.1 重新设计 C 板块 **3 模块**」<br>「**不写代码、不跑命令、不 commit**」<br>「**只做设计，不做实现**」「只碰 `docs/phase3-*` 和 `team/`」 |

**→ 授权文件说失效，角色卡说有效。执行者无法判断该听哪个。**

### 加重情节：改卡人只改了一半

改卡的人（知衡）**更新了角色卡的模块表**（三个模块 → 四个模块，对应 T-3 裁决），
**但没有同步职责与边界两节**。

→ **这本身就是一个信号**：改卡人对「要不要把该角色转成实现方」**并没有明确决定**，
只是顺口在授权文件里写了「可动范围」。**执行者若照授权文件动代码，可能越过了改卡人的真实意图。**

### 结论

**授权扩权时，必须同步改角色卡；否则不得据授权文件行动。**

**执行顺序**：
1. 先改角色卡（职责 + 边界 + 模块数）
2. 再下发扩权指令
3. 执行者据**改后的角色卡**行动

**若顺序颠倒** → 执行者**停下来问**，不要自行选择「听授权文件」。

### 与 E-001 的关系

| | E-001 | E-002 |
| :-- | :-- | :-- |
| 冲突位置 | **同一份文件内**（禁命令 ↔ 授权 commit） | **两份文件之间**（角色卡 ↔ 决策台账 / 指令） |
| 根因 | 写指令时没做互斥检查 | 改口径时**只改了一处** |
| 处置 | 二选一 | **同步改齐，或停下问** |

### 通用检查（写扩权指令前过一遍）

- [ ] 被扩权角色的**角色卡**是否已同步？职责？边界？范围？
- [ ] 角色卡里有没有**残留的旧口径**（模块数、阶段名、权限）？
- [ ] 授权文件与角色卡**是否指向同一个权限集合**？
- [ ] 若有第三方执行者会读这两份文件，**他能不能得出唯一结论**？

## E-003：用 shell 重定向写源码文件，把文件写成 UTF-16

**日期**：2026-10-12
**发现人**：C 板块（设计 CTO）
**性质**：**工具误用导致的源文件损坏**。幸有备份，零损失。

### 现象

为判定「某守护用例在 HEAD 上是否本就失败」，我执行了：

```powershell
git show HEAD:backend/database.py > backend\database.py    # ❌ 危险
```

**PowerShell 的 `>` 默认写 UTF-16LE**（带 BOM + 大量 NUL）。结果：

```
ImportError while loading conftest 'backend\conftest.py'
E   SyntaxError: source code string cannot contain null bytes
```

**`database.py` 当场不可导入** —— 整个后端测试套件起不来。

### 为什么没造成损失

操作前做了 `Copy-Item backend\database.py backend\database.py.p301bak`，
一步 `Copy-Item` 即完整还原；并用三项校验确认：

| 校验 | 结果 |
| :-- | :-- |
| NUL 字节数 | `0` |
| `def get_last_interaction_at` 在位 | ✅ |
| `git diff --numstat` 仍为 `106 行新增` | ✅ 与失误前一致 |

### 结论

**不得用 shell 重定向写源码文件。** PowerShell 默认 UTF-16，写进去就是废文件。
（`cmd.exe` 的 `>` 是 ANSI 系，行为不同，**同样不可依赖**。）

### 需要「临时切到某版本验证」时的正确做法

| 场景 | 用 |
| :-- | :-- |
| 只是看一眼某版本内容 | `git show HEAD:path`（**只读、不重定向到源文件**） |
| 要在某版本上跑测试 | `git stash` → 跑 → `git stash pop` |
| 要并行比较两个版本 | `git worktree add <临时目录> <ref>` |
| 必须落到文件 | 用**编辑工具**写（保证 UTF-8），或 `git checkout <ref> -- <path>`（git 自己管编码） |

### 通用检查（动工作树源文件前过一遍）

- [ ] 这条命令**会覆盖工作树里的源文件**吗？
- [ ] 覆盖前**有备份**吗？备份能**一步还原**吗？
- [ ] 我是不是可以用**只读**方式拿到同样信息（`git show` / `git diff`）？
- [ ] 写文件用的是**编辑工具**还是**shell 重定向**？后者在 PowerShell 下是 UTF-16。

### 与 E-001 / E-002 的关系

| | E-001 | E-002 | **E-003** |
| :-- | :-- | :-- | :-- |
| 类别 | 指令矛盾 | 文件间矛盾 | **工具误用** |
| 根因 | 没做互斥检查 | 改口径只改一处 | **不了解 shell 的默认编码** |
| 后果 | 执行者无法判断 | 执行者无法判断 | **文件损坏、套件起不来** |
| 防线 | 二选一 | 同步改齐 | **先备份 + 优先只读** |
