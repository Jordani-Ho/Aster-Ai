## E-001：禁止项与授权项互斥未二选一

**日期**：2026-10-04
**提出人**：发起人（本人在 C 板块启动指令的复盘中主动指出）
**记录人**：C 板块设计

### 原指令缺陷

C 板块启动指令的边界一节里，同时出现两条互斥的约束：

| 原文 | 冲突点 |
| :-- | :-- |
| 「不跑命令」 | 禁止执行任何命令 |
| 「不 commit」 | 隐含「可以 commit，只是本步不做」——而 commit **必须**经命令执行 |

两条并列时，执行者无法判定：是「任何情况下都不能跑命令」，还是「本步不跑，但允许 commit」。
若指令中另有「授权 commit」字样，则与「不跑命令」**直接矛盾**，执行者必须自行选择违背哪一条。

### 结论（发起人定）

**「禁命令」与「授权 commit」互斥，二选一。今后写指令不得同时出现。**

- 要授权 commit → 不得写「不跑命令」。
- 要禁止命令 → 不得写任何形式的 commit 授权。

### 推广：同类互斥对

写指令前检查，下列各组**只能选一个**：

| A | B | 说明 |
| :-- | :-- | :-- |
| 禁命令 / 不跑命令 | 授权 commit / 授权跑测试 / 授权安装依赖 | 「禁命令」是总闸，任何需要执行动作的授权都与它互斥 |
| 只读 | 落盘 / 新建文件 / 改写文件 | 「本次只读」与「产出文件」互斥，除非明确分阶段 |
| 不 commit | 授权 commit | 字面互斥 |
| 不写代码 | 授权修改 `.py` / `.ts` 源文件 | 源文件即代码 |

### 反面样板

> 「你不写代码，不跑命令，不 commit。…… 完成后授权 commit。」

### 正面样板（二选一）

> 「本次只读：不改任何文件，不跑命令，不 commit。回报即可。」

或

> 「本次可落盘 + 可 commit：写 `docs/xxx.md`，跑 `pytest` 验证，验证通过后 commit。」

或（**分阶段**，推荐用于大任务）

> 「第一步只读回报，不改文件、不跑命令。
> 第二步（等确认后）授权落盘 + 跑测试 + commit。」

### 对分阶段指令的补充要求

分阶段时，**每一步的边界必须单独写清**，不得用一句总边界覆盖全程。
否则第二步的授权会与第一步的禁令冲突，重演 E-001。

## E-002：授权文件改了口径，角色卡没跟着改

**日期**：2026-10-04
**发现人**：C 板块（设计 CTO）
**性质**：E-001 的**变体**——不是同一份文件内互斥，而是**两份文件之间**矛盾，且**都被标为"当前有效"**。

> **✅ 处置结果（2026-10-04）**：已上报发起人，**发起人裁定**：
>
> > 「**之前的边界是前任知衡的规定，现在的边界以现任知衡给你的指令为准。**」
>
> ⇒ **裁定原则：角色/边界类冲突，以「现任责任人的指令」为准，不以历史角色卡为准。**
> ⇒ 本条的**检查清单仍然有效**（用于防止下次再出现同类冲突），但**冲突时的仲裁规则已明确**。

### 现象

| 文件 | 内容 |
| :-- | :-- |
| `team/decisions/decision-log.md` **D-035** | 「前任 C 板块角色卡中的『只碰 `docs/phase3-*` 和 `team/`』『**不写代码、不跑命令、不 commit**』——**均属前任会话约束，现已失效**」 |
| `team/instructions/INSTR-2026-10-04-03` | 要 C 板块**写 `backend/` 代码 + 跑 pytest + 产 `migrations/*.sql`** |
| `team/roles/C板块设计.md` **L34–46** | 仍然写着：「按白皮书 v2.1 重新设计 C 板块 **3 模块**」<br>「**不写代码、不跑命令、不 commit**」<br>「**只做设计，不做实现**」「只碰 `docs/phase3-*` 和 `team/`」 |

**→ 授权文件说失效，角色卡说有效。执行者无法判断该听哪个。**

### 加重情节：改卡人只改了一半

改卡的人（知衡）**更新了角色卡的模块表**（三个模块 → 四个模块，对应 T-3 裁决），
**但没有同步职责与边界两节**。

→ **这本身就是一个信号**：改卡人对「要不要把该角色转成实现方」**并没有明确决定**，
只是顺口在授权文件里写了「可动范围」。**执行者若照授权文件动代码，可能越过了改卡人的真实意图。**

### 结论

**授权扩权时，必须同步改角色卡；否则不得据授权文件行动。**

**执行顺序**：
1. 先改角色卡（职责 + 边界 + 模块数）
2. 再下发扩权指令
3. 执行者据**改后的角色卡**行动

**若顺序颠倒** → 执行者**停下来问**，不要自行选择「听授权文件」。

### 与 E-001 的关系

| | E-001 | E-002 |
| :-- | :-- | :-- |
| 冲突位置 | **同一份文件内**（禁命令 ↔ 授权 commit） | **两份文件之间**（角色卡 ↔ 决策台账 / 指令） |
| 根因 | 写指令时没做互斥检查 | 改口径时**只改了一处** |
| 处置 | 二选一 | **同步改齐，或停下问** |

### 通用检查（写扩权指令前过一遍）

- [ ] 被扩权角色的**角色卡**是否已同步？职责？边界？范围？
- [ ] 角色卡里有没有**残留的旧口径**（模块数、阶段名、权限）？
- [ ] 授权文件与角色卡**是否指向同一个权限集合**？
- [ ] 若有第三方执行者会读这两份文件，**他能不能得出唯一结论**？

## E-003：用 shell 重定向写源码文件，把文件写成 UTF-16

**日期**：2026-10-12
**发现人**：C 板块（设计 CTO）
**性质**：**工具误用导致的源文件损坏**。幸有备份，零损失。

### 现象

为判定「某守护用例在 HEAD 上是否本就失败」，我执行了：

```powershell
git show HEAD:backend/database.py > backend\database.py    # ❌ 危险
```

**PowerShell 的 `>` 默认写 UTF-16LE**（带 BOM + 大量 NUL）。结果：

```
ImportError while loading conftest 'backend\conftest.py'
E   SyntaxError: source code string cannot contain null bytes
```

**`database.py` 当场不可导入** —— 整个后端测试套件起不来。

### 为什么没造成损失

操作前做了 `Copy-Item backend\database.py backend\database.py.p301bak`，
一步 `Copy-Item` 即完整还原；并用三项校验确认：

| 校验 | 结果 |
| :-- | :-- |
| NUL 字节数 | `0` |
| `def get_last_interaction_at` 在位 | ✅ |
| `git diff --numstat` 仍为 `106 行新增` | ✅ 与失误前一致 |

### 结论

**不得用 shell 重定向写源码文件。** PowerShell 默认 UTF-16，写进去就是废文件。
（`cmd.exe` 的 `>` 是 ANSI 系，行为不同，**同样不可依赖**。）

### 需要「临时切到某版本验证」时的正确做法

| 场景 | 用 |
| :-- | :-- |
| 只是看一眼某版本内容 | `git show HEAD:path`（**只读、不重定向到源文件**） |
| 要在某版本上跑测试 | `git stash` → 跑 → `git stash pop` |
| 要并行比较两个版本 | `git worktree add <临时目录> <ref>` |
| 必须落到文件 | 用**编辑工具**写（保证 UTF-8），或 `git checkout <ref> -- <path>`（git 自己管编码） |

### 通用检查（动工作树源文件前过一遍）

- [ ] 这条命令**会覆盖工作树里的源文件**吗？
- [ ] 覆盖前**有备份**吗？备份能**一步还原**吗？
- [ ] 我是不是可以用**只读**方式拿到同样信息（`git show` / `git diff`）？
- [ ] 写文件用的是**编辑工具**还是**shell 重定向**？后者在 PowerShell 下是 UTF-16。

### 与 E-001 / E-002 的关系

| | E-001 | E-002 | **E-003** |
| :-- | :-- | :-- | :-- |
| 类别 | 指令矛盾 | 文件间矛盾 | **工具误用** |
| 根因 | 没做互斥检查 | 改口径只改一处 | **不了解 shell 的默认编码** |
| 后果 | 执行者无法判断 | 执行者无法判断 | **文件损坏、套件起不来** |
| 防线 | 二选一 | 同步改齐 | **先备份 + 优先只读** |

## E-004：把 nostr-tools 的 `verifyEvent` 缓存当成内容校验

**日期**：2026-10-17
**发现人**：DeepSeek（M1-14a 康币账本施工）
**性质**：库的隐式缓存导致“内容被改后仍被判为已验证”。

### 现象

`nostr-tools` 的 `verifyEvent(event)` 通过后，会把 `Symbol("verified") = true` 写到事件对象上。
之后用对象展开复制事件再改内容，例如：

```js
const tampered = { ...event, content: 改过的内容 }
verifyEvent(tampered) // true，因为 Symbol 缓存被一起复制过去了
```

缓存被展开复制带走，`verifyEvent` 直接返回缓存的 true，不会重算事件 id。账本的篡改测试因此一度漏报。

### 为什么危险

- 账本、病历、评价都依赖“签名 = 内容不可改”；缓存绕过会让篡改静默通过。
- 只在“先验证过一次、再复制并修改”的路径出现，普通测试不一定覆盖，容易被误以为安全。
- 这类缓存是库的实现细节，升级版本后行为可能变化；不能把它当协议保证。

### 正确做法

- 验证时先重算 `getEventHash(event) === event.id`，再逐字段重建不含缓存 Symbol 的标准事件对象验签（tags 也复制）。只重算 id 仍不够：sig 不参与 id 哈希，改签名时缓存会继续误判；不能用对象展开重建验证对象。
- 回归测试同时覆盖改金额和只改 sig；必须先验证一次再复制篡改。
- 不要用“复制旧事件再改字段”的方式造新事件；要独立事件就重新构造并重新签名。
- 用任何“校验后缓存结果”的库函数前，先确认它缓存的是内容还是对象；缓存结果不能替代内容绑定校验。

## E-005：把 nostr-tools 的事件对象直接写进本地加密存储

**日期**：2026-10-17
**发现人**：DeepSeek（M1-15a 串联施工）
**性质**：库的实现细节与严格存储校验不匹配；测试替身掩盖了真实存储上的失败。

### 现象

1. `nostr-tools` 的 `finalizeEvent` 会在事件对象上挂 `Symbol("verified")`。本地加密存储只接受严格 JSON 值，`Reflect.ownKeys` 见到 symbol 键就报“JSON 属性无效”。M1-11 的 `completeSigning` 直接把签名事件存进 `pending-handover`，在真实 `LocalStore` 上会整条失败；此前测试用内存 `Map` 替身，所以没暴露。
2. `modificationLog` 用 `'source' in value` 判断 Field，把作业条目（有 `source`、没有 `value`）误当 Field，取 `.value` 得到 undefined，`case-book` 写入失败。

### 正确做法

- 签名事件落盘或放进信封前先 `JSON.parse(JSON.stringify(event))`（顺带去掉 E-004 的缓存 Symbol）；不要用对象展开复制。
- 判断 Field 要同时看 `value` 和 `source` 两个键。
- 至少有一条集成测试跑真实 `LocalStore`（fake-indexeddb），不能只用内存 Map 替身。

### 通用检查（写“签名事件落盘 / 修改记录”代码前过一遍）

- [ ] 要落盘的 nostr 事件是否经过 JSON 往返？
- [ ] `isField` 之类的鸭子类型是否只看了部分键？
- [ ] 签署→交还→写医案的路径，有没有用真实存储的测试覆盖？

## E-006：同源代理改写 Host，NIP-98 签名 URL 与网关校验 URL 不一致

**日期**：2026-10-17

**发现人**：Codex（M1-15b 测试环境）

**性质**：测试环境指令/验收遗漏了代理与签名 URL 必须一致的前提；框架施工时也没有先用快速合同测试核对。

### 现象

浏览器按页面地址签 NIP-98 的 `u`，Vite 字符串形式的代理配置把 Host 改成网关目标地址。
网关按收到的 Host 重建 URL，真实浏览器请求返回 401；直接访问网关的合同测试却全绿。
第一次真实 CI 中继已编译、4 条环境探针已通过，直到浏览器经代理请求时才发现。

### 正确做法与指令补充

- 同源测试代理显式 `changeOrigin: false`，保持签名的外部 URL 与网关收到的 Host 一致；
  部署采用其他反向代理时，也可按真实外部地址正确设置网关既有 `publicUrl`。
- 不能通过关闭 NIP-98、绕过成员校验或修改客户端已签名事件来“修”测试。
- “搭同源测试代理”指令应同时要求一条**经真实代理访问真实网关**的签名请求合同测试，不能只测直连。
- 原生编译与浏览器验收分开：成功编译先缓存，再跑浏览器断言，避免一个 HTTP 接线错误导致下次重编全部 Rust 依赖。

本次补上了真实 Vite 代理合同测试；只改测试配置，未改网关鉴权或任何业务规则。

## E-007：要求成员热更新，却沿用只读单文件挂载

**日期**：2026-10-17
**发现人**：Codex（M1-17）
**性质**：组合任务的部署前提没有同步：新卡要求成员名单原子写临时文件并rename、无需重启；前一卡却将成员文件以只读单文件挂载。

## E-009：要求复用交还与删除，却只验收了照片引用

**日期**：2026-10-17
**发现人**：Codex（M1-20 接通面诊）
**性质**：任务验收遗漏了附件归属变化。M1-12 要求复用签字交还、老师端删除照片，验收只检查签名病历与老师端删除，没有检查学生持有照片字节。

远程问诊的照片本来就在学生手机上，交还签名引用足够关联；面诊照片却由老师手机产生。照搬只发送 `AttachmentRef` 的路径后就删除，会让学生只收到引用、拿不到照片。

## E-011：能编码视频，不代表能编码旁白音频

**日期**：2026-10-18
**发现人**：Codex（M1-23b）

WebCodecs 的 VideoEncoder / AudioEncoder 存在，甚至 H.264 能编码，都不能证明 AAC 编码可用。
本次 Chromium 实测拒绝 AAC 配置，但能播放带 AAC 的原片。压缩必须核对真实转换结果和被丢弃的轨道；
任一原有旁白轨道不能转换时，回退整段原片，不能悄悄丢声音。验收 fixture 应事先生成带声的合成 MP4，
不能让浏览器自己造不支持的 AAC，或改成静音片再声称互播通过。真机矩阵必须另记实际设备结果。

## E-012：小照片的字符串和列表写法扛不住几十 MB 视频

**日期**：2026-10-18
**发现人**：Codex（M1-23b）

逐字节拼 Base64 字符串会产生大量临时对象；带重复分组的整串 Base64 正则可能在大文件上耗尽栈。

不能每次读取设置都 getAll 整库视频。测试要真的使用 20 MiB 数据覆盖存储及文件备份恢复。

用 Buffer.compare（或完整摘要）比较全部字节，避免为每个元素构造断言树。不是扩大堆或缩小验收文件掩盖问题。
