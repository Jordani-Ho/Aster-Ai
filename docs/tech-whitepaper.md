## 0. 一页纸总结

1. **数据跟着人走。** 学生的一切（病历、照片、语音、作业）存在学生自己的手机上；老师的一切（模板、医案、思路）存在老师自己的手机上。**所有人只用手机，没有中心数据库。**
2. **老师端只留八字。** 诊断时临时拿到学生的资料，签完字把完整病历交还学生，原始资料随即销毁（“诊毕即还”）。
3. **AI 只起草、不定论、不签字。** 诊断和方案的最终决定只属于老师本人，签字的永远是真人老师。学生智能体遇到急重症信号，第一句话永远是“请立即去医院”。
4. **中间只有可替换的“邮差”。** 节点之间靠端到端加密的消息中继传话，中继看不懂内容、不长期存东西，任何人都能架一个。
5. **治理、数据、支付三层去中心化。** 治理靠引荐链和写死在代码里的封存规则，加上只来自真实学生的评价公示；数据靠第 1、2 条；支付用师生双签的康币账本起步，以后过渡到智能合约。

## 1. 设计原则

| # | 原则 | 含义 | 反例（不要做） |
| :-- | :-- | :-- | :-- |
| 1 | **大道至简** | 能不建就不建。规模是 10～20 位老师、数千名学生，不是大平台 | 为“以后可能”预建治理机构、哈希链 |
| 2 | **数据跟人走** | 谁的数据存在谁的设备上；交给别人看是临时授权 | 中心化数据库 + “权限隔离” |
| 3 | **真人签字** | AI 的一切输出都是草案；签字用老师本人的私钥 | AI 自动发方、自动回复医嘱 |
| 4 | **无中心、可替换** | 任何服务器组件都无状态、可被别人替换 | 某台服务器宕机，整个社区停摆 |
| 5 | **模型无关** | 提示词、模板、数据格式是标准文件，换哪家大模型都能跑 | 业务逻辑写死在某家模型的私有特性上 |
| 6 | **诚实边界** | 文档只写已实现的东西为“已实现” | v2.1 把 Whisper、视觉模型、RAG 写成“已完成”，代码里并没有 |

## 2. 角色与节点

每个真人都是一个**节点**：一对密钥 + 一个手机网页应用 + 一个智能体。**所有使用者只用手机**：手机浏览器打开同一个网址，按身份显示老师或学生界面，不用下载安装。

| 角色 | 设备 | 智能体 | 一句话 |
| :-- | :-- | :-- | :-- |
| 学生 | 手机 | 学生智能体 | 镜子 + 辅导员：采集、整理、督促、提醒，**不推理** |
| 老师 | 手机 | 老师智能体 | 学徒 + 助理：起草病历、辨证和方案，打理杂务，**不签字** |
| 被照护者 | 挂在学生节点下 | 共用学生智能体（监护模式） | 子身份，密钥由监护人的助记词派生 |
| 徒弟（M3） | 手机 | 徒弟智能体 | 老师智能体的镜像，用于训练 |

**身份**：一对 secp256k1 密钥，用 12 个助记词备份（BIP-39）。公钥就是身份 ID，**名字只是本地显示用的称呼**，不再用名字当主键。

## 3. 总体架构

```
   学生节点（手机）                                   老师节点（手机）
 ┌───────────────────┐                           ┌───────────────────┐
 │ 学生智能体          │                           │ 老师智能体          │
 │ 本地加密存储：      │   端到端加密的签名消息      │ 本地加密存储：      │
 │  完整病历/照片/语音 │ ◄──────────────────────►  │  模板 / 医案库      │
 │  作业/打卡/趋势     │      （经由中继转发）        │  学生常驻档案(八字) │
 └─────────┬─────────┘                           └─────────┬─────────┘
           │                                               │
           │            ┌──────────────────────┐            │
           ├──────────► │ 中继（可多个，可替换） │ ◄──────────┤
           │            │ 只转发、不解密、限期删 │            │
           │            └──────────────────────┘            │
           │            ┌──────────────────────┐            │
           └──────────► │ 模型网关（可选）       │ ◄──────────┘
                        │ 转发到大模型，不记录   │
                        └──────────────────────┘
```

整个系统**只有五种部件**：

| 部件 | 是什么 | 谁来运行 | 有没有状态 |
| :-- | :-- | :-- | :-- |
| 手机网页应用 | 同一套 React + TypeScript 代码，以网页应用（PWA）形式运行在手机浏览器里 | 每个人自己 | 有（本人数据，存在手机浏览器里，加密） |
| 中继 | 现成的开源 **Nostr** 中继软件 | 社区先运行 1～2 个，任何人可加 | 只有待投递的加密消息，到期删除 |
| 模型网关 | 一个很薄的转发服务，把智能体请求转给大模型 | 社区（公益期）或老师自备 | 无，**不记录内容** |
| 推送服务 | 有新消息时提醒对方（只说“有新消息”，不带内容） | 社区 | 只有推送订阅令牌 |
| 社区目录 | 一组签名事件：谁是老师、谁引荐了谁、评价、封存 | 存在社区中继上，**只对成员公钥开放读取**；每个客户端自行计算 | 成员可见、可验证 |

**为什么选 Nostr**：它正好提供本项目需要的三样东西，而且全是现成的：
- 公私钥身份；
- 签名事件加中继转发，带端到端加密私信；
- 与比特币闪电网络的支付对接。

它的密钥曲线和比特币相同，第 8 章的支付预留因此几乎零成本。**不自建区块链。** 需要“不可篡改”的记录（引荐、封存）用签名事件即可；要更强的时间证明，可以把事件哈希锚定到比特币（OpenTimestamps），这一步放到 M3。

> 开发者注意：Nostr 的具体协议编号（NIP）请以官方仓库的当前版本为准，选用其中“签名事件、加密私信、礼物包裹、中继鉴权”相关的规范，不要自造加密格式。
> 推送服务用标准的网页推送（Web Push）。iOS 只有在用户把网页“添加到主屏幕”后才支持推送；不支持的环境（比如微信内置浏览器）打开应用时自动同步。推送服务是唯一知道“某台设备属于某个公钥”的组件，所以必须做到不记录消息内容、令牌可以随时注销。

## 4. 数据：谁存什么

### 4.1 存放表

| 数据 | 存在哪 | 谁能看 | 何时删除 |
| :-- | :-- | :-- | :-- |
| 姓名、联系方式、出生年月日时与地点 | 学生手机 | 只有学生本人 | 学生决定 |
| 症状陈述、舌象/面色照片、语音、打卡 | 学生手机 | 学生；问诊时临时授权给某位老师 | 学生决定 |
| 签字病历（完整） | 学生手机 | 学生；复诊时临时授权 | 学生决定 |
| **学生常驻档案**：称呼、性别、年龄、**八字**、居住城市 | 老师手机 | 该老师 | 老师把学生移出门下时删除 |
| 问诊包（临时收到的原始资料） | 老师手机（临时） | 该老师 | **签字发回后立即销毁** |
| 医案（去标识）：抽象症状、辨证、方、修改记录 | 老师手机 | 该老师（知识产权） | 老师决定，可传承 |
| 老师模板（问诊、病历、施治、开方） | 老师手机 | 该老师 | 老师决定，可传承 |
| 康币账本（该师生之间的每一笔账） | 师生双方手机，各存一份 | 该老师与该学生 | 不删除 |
| 引荐、邀请关系、评价、封存事件 | 社区中继（签名事件） | 社区成员 | 不删除（只有公钥，没有隐私内容） |

### 4.2 八字最小化

学生智能体在本地把出生时间和地点换算成八字（四柱），**只把八字和年龄发给老师**，原始出生时间不出手机。年龄在每次问诊时自动重新计算，不会过期。
- 时辰未知时只发三柱，并注明“时柱缺”。
- 是否做真太阳时修正，由老师在模板里设置，换算仍在学生端完成。
- 换算逻辑必须有单元测试，用万年历上的已知样例核对。

### 4.3 诊毕即还（取代“阅后即焚”）

```
学生确认发送 ─► 老师收到问诊包 ─► 智能体起草 ─► 老师修改、签字
                                                    │
                       完整签字病历加密发回学生 ◄──────┤
                                                    │
                  老师端：保留去标识医案；问诊包销毁 ◄─┘
```

- “销毁”指客户端删除本地文件和缓存，并写一条本地日志。
- **诚实边界**：软件只能保证自己删除，挡不住老师截图或抄录。这一层靠老师本人的操守，与线下看诊相同。

### 4.4 备份

数据只在个人设备上，丢手机就等于丢病历；网页应用的数据存在浏览器里，清理浏览器缓存同样会丢。所以备份是**强制流程**，不是可选功能：
- 首次使用必须完成助记词抄写，并通过核对；
- 应用启动时向浏览器申请“持久化存储”，减少被系统自动清理的可能；
- **默认开启**：每天把**加密备份**存到社区中继，只保留最近 3 份，只有本人的密钥能解开。换手机、清缓存后，输入助记词即可恢复；
- 另外每月提醒一次，导出一份加密备份文件，由用户存到自己选的地方。

照片在手机上压缩（长边不超过 1280 像素）后再存储和发送，控制空间占用。

## 5. 核心闭环

### 5.1 三种问诊场景，共用一条链路

| 场景 | 说明 | 里程碑 |
| :-- | :-- | :-- |
| 时差远程 | 学生随时提交，老师有空时处理 | **M1** |
| 面诊记录 | 老师当面看诊，老师端录音、拍照、起草，签字后发给学生 | **M1** |
| 实时远程 | 预约后双方在线 | M2 |

### 5.2 一次问诊的步骤

1. **采集**：学生对手机说话、拍舌象，学生智能体按老师的问诊模板（默认十问歌）追问缺失项。
2. **急症筛查**：每次采集都过一遍急症红线（见 5.4），命中就中断流程，直接提示就医。
3. **整理与确认**：智能体把口语整理成陈述，**学生点“确认发送”**。这是数据离开手机的唯一入口。
4. **授权范围**：学生选择附带哪些历史病历（默认：同一位老师的近 3 次病历）。
5. **起草**：老师智能体结合老师模板、八字、节气时令、老师自己的医案库，起草病历、辨证、施治方案（含作业）和方子。
6. **签字**：老师修改后用私钥签字，生成签字病历。
7. **交还**：签字病历加密发回学生，方案里的作业自动进入学生智能体的提醒日程。
8. **销毁与学习**：老师端销毁问诊包，保存去标识医案和“草案 → 定稿”的修改记录。
9. **日常**：学生智能体按作业、子午流注和节气提醒打卡，生成趋势图；学生想复诊时回到第 1 步。

### 5.3 病历格式（吸收自 MAP-TCM 的 MAP-003、MAP-005）

一次问诊是一条 `Encounter` 记录：

```text
Encounter
├─ 基本：学生公钥、就诊类型（初诊 / 复诊 / 面诊）、时间、老师公钥
├─ 原始资料：主诉、现病史、既往史、用药与过敏、照片和语音引用
├─ 四诊：望、闻、问、切（允许“未采集”）
├─ 老师判断：证候、病机、辨证依据
├─ 处理：治则治法、方子与加减理由、作业（非药物建议）、医嘱
├─ 结果：疗效变化、不良反应、下次计划
└─ 审核：草稿 → 已签字；签字后再改只生成新版本，旧版本保留
```

规则：
1. **每个字段都带来源标签**：`学生陈述`、`老师判断`、`AI 草稿`、`外部证据`、`未知`。界面用颜色区分，AI 推测永远不能显示成事实。
2. **缺失就写“未知”**，AI 不得悄悄补全。
3. **改方要关联上一版方子**，并写明加减理由。这正是思想指纹最有价值的部分。
4. 签字后的病历**不可覆盖**。改动生成新版本，作废只标记失效，不删除历史。

### 5.4 急症红线（硬规则，任何配置都不能关闭）

学生智能体在采集和日常对话中，一旦发现下列信号，**立即停止其他流程**，显示“请立即就医 / 拨打当地急救电话”，并通知该生的老师：
- 胸痛、胸闷，伴有出汗或放射痛；
- 一侧肢体无力、口角歪斜、言语不清；
- 呼吸困难、意识改变、抽搐；
- 高热不退、剧烈头痛、剧烈腹痛；
- 大出血、孕期出血、严重外伤；
- 表达自伤或轻生念头（引导联系当地心理援助热线）。

红线清单是一个独立的配置文件，必须配有测试用例。只能增加条目，不能删除；修改需要发起人同意。

## 6. 智能体规范

### 6.1 铁律（写进代码，不只写进提示词）

| 智能体 | 可以 | 不可以 |
| :-- | :-- | :-- |
| 学生智能体 | 采集、整理、提醒、展示趋势、讲**公共**养生知识（节气、作息、饮食通则）、转述老师已签字的医嘱 | 诊断、推理病因、建议用药、修改医嘱 |
| 老师智能体 | 起草病历、辨证和方案、方子草案；打理预约、库存等杂务 | 签字；把任何内容未经签字发给学生 |

实现要求：
- **签字**只能由老师本人在界面上操作触发，私钥调用路径里不允许有 AI 调用。
- 学生端只显示带有效老师签名的医嘱。

### 6.2 学习闭环与“思想指纹”

v3 对“思想指纹”给出可实现的定义：

> **思想指纹 = 老师的模板 + 老师的去标识医案库 + 每次“草案 → 定稿”的修改记录。**

- **M1**：起草时，把这三样作为上下文交给大模型（检索最相近的医案作为范例）。**不做模型微调。**
- **一致率**：每次签字时自动记录草案与定稿的差异，老师可以看到“智能体越来越像我”的曲线。
- **放权开关**（取代五阶段）：老师自己决定智能体起草哪些部分，从默认的“只起草病历”逐步加到“辨证建议”“方子草案”。无论哪一档，都必须签字。

### 6.3 模型无关与自修复

- 所有提示词、模板、红线、领域知识都是 `prompts/`、`templates/`、`domain/` 下的**纯文本或 JSON 文件**，与代码分离。
- 每个客户端内置一份**给 AI 看的运维手册** `OPERATIONS.md`，并提供一个自检命令，检查密钥、中继连通、模型配置和备份状态。老师用自己的智能体就能读懂手册、排查配置问题。
- 模型配置是每个节点自己的：可以用社区的模型网关，也可以填自己的 API Key，或者接本地模型。
- **诚实边界**：使用云端大模型时，智能体请求的内容会经过模型服务商。看重这一点的用户可以选择本地模型。

## 7. 治理去中心化

### 7.1 三种门（都是签名事件）

| 门 | 谁签 | 效果 |
| :-- | :-- | :-- |
| 引荐 | 现任老师签“我为某公钥背书” + 一句话理由 | 被引荐者成为老师 |
| 邀请 | 老师签邀请；学生接受，生成双签的师生关系 | 学生入该老师门下 |
| 监护 | 学生为被照护者派生子身份 | 子身份挂在监护人节点下 |

- **创世纪**：发起人的密钥签发第一批老师。之后所有老师都来自引荐链。
- 一个学生最多同时跟随 5 位老师。老师之间看不到学生在其他门下的任何内容。

### 7.2 评价（真实问诊才能评价）

- 每张签字病历都有唯一哈希。学生凭这个哈希提交一条评价，**一次问诊只能评一次**，之后可以修改一次（比如疗效要过一段时间才看得出来）。
- 评价只有两个维度，都是事实描述，不带情绪：

| 维度 | 选项 |
| :-- | :-- |
| 疗效 | 快 / 慢 / 无 |
| 收费 | 高 / 中 / 低 |

- 评价必须对应一张真实签字的病历，所以刷好评、恶意差评都做不了。
- 评价用于公示（第 7.5 节）；其中疗效评价长期为“无”会触发老师封存（第 7.3 节）。收费评价只公示。
- 已知局限：老师知道自己学生的公钥，评价对老师并不匿名。M2 评估是否引入匿名评价。

### 7.3 封存（代码执行）

**老师封存**：规则写死在社区代码里，每个客户端根据签名事件自行判定，满足任一条件即显示为“已封存”。封存后不再列出、不再转发问诊，其智能体停止对外服务。

| 条件 | 判定方式 | 默认标准 |
| :-- | :-- | :-- |
| 活跃度不足 | 最近 3 年（考察期）内签字问诊的次数 | 少于 12 次 |
| 学生人数不足 | 最近 3 年内有过签字问诊的不同学生数 | 少于 3 人 |
| 疗效长期为“无” | 最近 3 年内收到的疗效评价 | 至少 20 条，且“无”超过一半 |
| 引荐人撤回背书 | 唯一引荐人签发“撤回”事件，30 天内无其他老师补签 | — |

- 考察期从老师入社区之日起算，满 3 年后开始判定活跃度和学生人数，此后每天按“最近 3 年”滚动计算。新老师头 3 年不会因为活跃度或学生人数被封存。
- 疗效条件不受头 3 年限制，但必须累计满 20 条评价才判定，避免少数评价决定一位老师的去留。
- 解封：任一现任老师签发新的背书。解封后重新开始一个 3 年考察期。

**学生封存**（只限本门）：由**老师智能体**按老师自己设定的门规自动执行，学生在其他老师门下不受影响。

| 门规条件 | 老师可设定的参数 | 默认 |
| :-- | :-- | :-- |
| 长期不活跃 | 多少天没有打卡或问诊 | 180 天 |
| 长期欠费 | 康币余额为负、持续多少天 | 60 天 |

- 执行前 7 天，智能体先提醒学生和老师；执行后通知老师，老师可以一键撤销。
- 学生被封存后，老师端删除该生的常驻档案；学生的数据始终在学生手里。
- 解封：该老师重新邀请。

> 所有默认标准都放在配置文件里，改动需要发起人确认。老师封存的标准对全社区统一、事先公开；学生封存的标准由各位老师自己定。

### 7.4 智能体传承（M3）

- 老师可以随时签一条“继承设定”事件，指定继承者。以最后一次为准。
- 智能体资产就是 6.2 的三样文件，传承即把加密包交给继承者。继承后的智能体改名为“某某门智能体”，不能冒充原老师签字。
- 老师未指定继承者时，资产封存，等待引荐链上的老师认领。“思想相似度自动选继承者”推迟，暂不实现。

### 7.5 公示栏（M2）

- **谁能看**：只对社区成员开放（社区中继只向成员公钥提供读取），不对外公开，不做推广。
- **老师自填**：擅长的调理方向，从一份标签表里选（例如“视力调理”“脊柱调理”“备孕调理”），可以加一句话说明。标签表放在 `domain/tcm/` 里，老师可以申请新增。
- **学生评价**：每位老师每个擅长方向下，展示疗效（快 / 慢 / 无）和收费（高 / 中 / 低）各自的人次分布，以及评价总数。
- **起始门槛**：某个方向累计满 10 条评价才显示分布，否则只显示“评价不足”。避免样本太少造成误导。
- **计算方式**：没有中心评分服务器，每个客户端根据签名事件自己计算，结果人人可以复核。
- **措辞**：擅长项写“调理方向”，不写“治愈”“包治”之类的疗效承诺。

## 8. 支付去中心化：康币

### 8.1 为什么保留

药材需要提前采购，学生来自五湖四海。预付是老师对自己付出的保护。现实中已经有“学生充值、老师赠送积分”的做法，康币把它记清楚。

### 8.2 第一阶段：师生双签账本（M1 起）

- **社区不经手钱款。** 钱在社区外走（转账、现金、任何方式），康币只是账。
- **每位老师一本账。** 康币记在“某位老师 × 某位学生”之间，不能在老师之间流通或转让。这样不需要任何中心发行方，也不需要兑换所。
- **计价**：每位老师自己声明“1 康币 = 多少钱”和价目（看诊、药材、代煎等），写在自己的资料里。
- **四种记账事件**，每条都签名，师生手机各存一份：

| 事件 | 谁签 | 说明 |
| :-- | :-- | :-- |
| 充值 | 老师确认收款后签 | 学生在社区外付款，老师确认后记入 |
| 赠送 | 老师签 | 老师送给学生的康币 |
| 扣费 | 老师签，附签字病历或药材清单的哈希 | 学生 7 天内可以对某一条提出异议 |
| 退款 | 老师签 | 冲正或退还 |

- **余额** = 所有事件按顺序累加，两部手机算出的结果必须一致。每条事件引用上一条的哈希，任何一方删改都会被对方发现。
- **异议**：学生对某条扣费点“有异议”，账本上就会标记出来，师生自己协商。社区不仲裁，异议记录只有双方可见。
- **隐私**：账目只在师生两人之间。公示栏只显示“收费高 / 中 / 低”的评价分布，不显示金额。

### 8.3 第二阶段：智能合约托管（M3 以后）

- 学生把预付款存入一个智能合约托管，看诊签字后，合约按扣费事件自动划给老师；未用完的部分学生可以取回。
- 第一阶段的四种事件和第二阶段的合约动作**一一对应**，迁移时只需把历史账本重放一遍，老师和学生不用改变习惯。
- 用哪种通证（比特币闪电网络、稳定币或其他）待发起人决定。身份密钥已经和比特币同曲线，接入成本低。
- 在此之前，系统里不出现任何真实货币的支付接口。

## 9. 技术选型

| 层 | 选型 | 理由 |
| :-- | :-- | :-- |
| 客户端 | React + TypeScript（沿用） | 一套代码同时覆盖 iOS 和安卓，老师和学生共用 |
| 手机端分发 | M1、M2 做**网页应用**：一个网址，手机浏览器打开，可“添加到主屏幕”。在微信里打开时，引导用户转到系统浏览器 | 零安装、零审核，测试者意愿最高；原生 App 或小程序等内测验证后再定 |
| 本地存储 | 浏览器 IndexedDB，整库加密，申请持久化存储；加密备份默认存中继（第 4.4 节） | 数据只在本地，备份兜底 |
| 加密与身份 | secp256k1 + BIP-39；成熟的 Nostr 客户端库 | 不自造加密 |
| 中继 | 开源 Nostr 中继软件，直接部署，开启成员鉴权 | 不自写服务器 |
| 推送 | 标准网页推送（Web Push），经一个很薄的推送转发服务 | 不依赖任何应用商店 |
| 部署位置 | 网页、中继、模型网关、推送服务放在中国大陆和美国都能顺畅访问的地区，具体机房在 M0 实测后选定 | 老师和学生分布在两地 |
| 模型网关 | 约 100 行的无状态转发服务，不落日志 | 学生不需要自己申请 API Key |
| 大模型 | 可配置：DeepSeek / Claude / OpenAI 兼容接口 / 本地模型 | 模型无关 |
| 语音转文字 | M1 用系统或浏览器自带的语音识别（现有代码已用） | 先能用；更好的方案以后再换 |
| 历法与八字 | 成熟的农历和八字开源库（TS 版），配合万年历样例测试 | 替代现有的 Python `cnlunar` |
| 测试 | Vitest（单元）+ Playwright（端到端，两个模拟节点互发问诊和记账） | 闭环必须能自动跑通 |

**为什么先不做微信小程序**：
- 小程序连接的服务器域名需要在微信后台登记，面向大陆的通常还要求域名备案；
- 健康、医疗相关的类目往往要求主体资质，个人主体受限；
- 本地存储空间很小（约 10 MB），放不下照片；
- 每次发版都要过微信审核。

网页应用没有这些门槛，同一个网址在微信里也能打开。等内测验证了需求，再决定是否做小程序或原生 App。网页应用的代码可以复用。

**不用的东西**：FastAPI 业务后端、中心数据库、LangGraph、自建区块链、9 个功能开关。

## 11. 开发协作与审核

| 角色 | 由谁担任 | 职责 | 不做 |
| :-- | :-- | :-- | :-- |
| 发起人 | 真人 | 哲学和产品拍板；确认第 7.3、5.4 的参数 | 不需要看代码 |
| 技术合伙人 | Claude | 维护本白皮书；拆分任务卡；**审核每一次合并**；里程碑验收 | 不审核自己写的代码 |
| 施工者 | Codex / DeepSeek | 按任务卡实现并自测 | 不改本白皮书；不审核自己的代码 |

规则：
1. **施工的人不审自己的代码。** 每次合并都由另一个智能体审核：施工者是 Codex，就由 Claude 审，反之亦然。
2. **每张任务卡先写验收用例。** 可以由审核者先写测试，施工者让测试通过。
3. **文档预算**：本白皮书不超过 1 万字。`team/` 目录只保留三样：任务卡、发起人决策记录（只记发起人拍板的事）、错题本。
4. **改白皮书**：技术白皮书由技术合伙人修改，并在文末“变更记录”登记；宪章只有发起人能改。
5. **仓库与分工**：见第 12.1 节。所有代码只通过合并请求进入主分支，由审核者合并。
6. **三级决策**（吸收自 MAP-TCM 的 MAP-002）：
   - **A 类**：可逆的小改动，例如界面文字、修 bug。施工者直接做，合并时说明。
   - **B 类**：数据格式、流程、对外措辞的改动。需要技术合伙人审核，并写进变更记录。
   - **C 类**：涉及急症红线、隐私、康币、宪章，以及封存规则的数值。必须由发起人决定。
7. **只用合成数据**：仓库、测试、日志、提交记录里不得出现任何真实学生的资料。
8. **`AGENTS.md`**：仓库根目录放一份给施工智能体读的规则文件，内容是本节的摘要。Codex 会自动读取它；`CLAUDE.md` 指向同一份文件。
9. **领域可扩展**：中医相关内容只放在 `domain/tcm/`（十问歌、八字、子午流注、红线、模板）。核心代码不写中医专有逻辑，以后做厨师、设计师等其他师承社区时，可以复用核心。**在第二个领域真正出现之前，不做通用化抽象。**

| P1 | 老师端“学生常驻档案”字段 | 称呼、性别、年龄、八字、居住城市 | ✅ 发起人确认 |
| P2 | 老师封存：考察期 / 活跃度 / 学生人数 | 3 年 / 少于 12 次签字问诊 / 少于 3 位学生 | 3 年由发起人确认；12 次约等于每季度一次 |
| P3 | 老师封存：疗效 | 3 年内至少 20 条疗效评价，“无”超过一半 | 发起人要求；20 条起判，避免小样本误伤 |
| P4 | 引荐人撤回后的补签期 | 30 天 | 订阅、域名等服务常见的 30 天宽限期 |
| P5 | 学生门规默认值 | 180 天不活跃 / 欠费 60 天 | 互联网服务通常以 6 个月未登录视为不活跃；老师可以自行修改 |
| P6 | 公示栏显示门槛 | 每个方向满 10 条评价 | 点评类平台常见的最低样本数 |
| P7 | 扣费异议期 | 7 天 | 参照电商“7 天无理由”的惯例 |
| P8 | 中继保存未投递消息 | 30 天，投递后即删 | 主流即时通讯软件对未送达消息的通行做法 |
| P9 | 中继保存加密备份 | 每人最近 3 份 | 控制中继存储量 |
| P10 | 照片压缩 | 长边不超过 1280 像素 | 足够看清舌象，单张约 200～400 KB |
| P11 | 一个学生同时跟随老师的上限 | 5 位 | 沿用 |
| P12 | 复诊默认附带的历史病历 | 同一位老师的近 3 次 | 沿用 |

**存储量估算**：
- 老师手机只留常驻档案和去标识医案，几千名学生也不到几十 MB。
- 学生手机主要是照片，每天一张，一年约 100 MB。
- 中继只放 30 天内未投递的消息和每人 3 份加密备份。

存储空间不是瓶颈。
