# V2-37 老师邀请制：核心成员推荐新老师

- 状态：待派（**Codex**）
- 依据：决策 2026-10-25（老师也是邀请制，由核心成员——发起人、技术合伙人和最早的几位老师——推荐师德可靠的人）；决策 2026-10-26（先只有发起人一位核心成员，最早的老师以后由发起人一一加进来；技术合伙人是智能体，没有签名身份，不算核心成员；被推荐的老师扫发起人签发的链接就能登记开馆，不再抄部署口令）
- 原则：推荐是一条签名事件，网关只认核心成员的签名；界面上不出现“密钥、公钥”。

## 现状（施工前先核对）

- 网关成员名单是一张平表，不分老师和学生；`validInvite` 只检查签名人在名单里——**学生也能签出进馆邀请**，这是漏洞，本卡一并补上。
- 第一位老师靠部署口令（`/invite/seed`，一次性）登记；第二位老师要部署方重新生成口令。

## 范围

1. **核心成员名单**（网关本机文件，和成员名单并列）：
   - 部署脚本生成一张一次性的“**核心成员登记**”链接 / 二维码（做法同 V2-31 的扫码登记）；发起人用自己的手机扫一次，就成为第一位核心成员。用过即作废，口令不进地址栏、不进日志。
   - 核心成员可以把**已登记的老师**加为核心成员（签名事件；在“我的馆 → 设置”或发起人的“我 → 设置”里一个按钮）。不做移除（以后再说）。
2. **推荐新老师**：
   - 核心成员在应用里点“**推荐一位老师**”→ 填一句“为什么推荐他” → 生成链接和二维码（7 天有效、只能用一次）。推荐是一条签名事件：签名人、被推荐人还不知道是谁（扫码时绑定）、理由、有效期、nonce。
   - 新老师打开链接 → 直接进入建馆引导，身份自动选“老师”；第 2 步“登记”不用口令，按钮直接是“登记，下一步”。
   - 网关新入口（例如 `/invite/teacher`）：核对签名人在核心名单里、未过期、未用过 → 把新老师登记为成员**并记为老师**，同时记下“谁推荐了谁、何时、理由”。
3. **老师与学生分开记**：网关成员名单里记下谁是老师；**进馆邀请只接受老师签发的**（补上面的漏洞）。旧的部署口令登记的老师照旧算老师。
4. **部署口令留作兜底**：没有核心成员时（新部署），仍可用 V2-31 的口令登记第一位老师。
5. **只有核心成员看得到“推荐一位老师”**：应用向网关问一句“我是不是核心成员”（签名请求），是才显示按钮。

## 不做

- 不做公示、评分、排行，不做老师封存（白皮书第 9 节）。
- 不做撤销推荐、移除核心成员。
- 推荐记录不在应用里对其他人展示，只存在网关本机文件里。

## 验收用例

1. 新部署：用“核心成员登记”链接登记发起人；同一链接再扫一次失败。
2. 发起人推荐一位老师 → 新老师扫码 → 建馆第 2 步不要口令即可登记 → 能开馆、能邀请学生。
3. 同一张推荐链接第二次使用失败；过期的失败；非核心成员签的失败（都给出看得懂的中文提示）。
4. **学生签出的进馆邀请，网关拒绝**；老师签的照常可用（回归 V2-15、V2-31）。
5. 发起人把这位老师加为核心成员 → 这位老师端出现“推荐一位老师”。
6. 学生端、普通老师端都看不到“推荐一位老师”。
7. 网关日志里不出现口令和推荐理由。
8. 两台手机真实中继 e2e：发起人推荐 → 新老师开馆 → 邀请学生进馆。
9. 只用合成数据；CI 三项全过。
