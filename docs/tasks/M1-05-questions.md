## 官方规范核对（2026-10-16）

- [NIP-17 私信](https://github.com/nostr-protocol/nips/blob/master/17.md)：kind 14 rumor，经 kind 13 seal 和 kind 1059 gift wrap；外层 p 标签是收件人公钥。
- [NIP-44 加密](https://github.com/nostr-protocol/nips/blob/master/44.md)：版本化加密规范，不自行设计格式。
- [NIP-59 礼物包裹](https://github.com/nostr-protocol/nips/blob/master/59.md)：外层用随机一次性密钥签名，路由标签包含收件人；支持 NIP-42 真实身份鉴权。
- [NIP-42 鉴权](https://github.com/nostr-protocol/nips/blob/master/42.md)：连接者使用身份密钥签署鉴权事件。
- [NIP-40 过期](https://github.com/nostr-protocol/nips/blob/master/40.md)：expiration 标签控制过期；不能据此保证投递后立即删除。

## 请求裁决

1. **隐私边界冲突（需发起人决定）**：验收 2 要求中继存储的事件看不到真实收件人公钥，但标准 NIP-17/59 的外层 p 标签公开该公钥；NIP-42 又向中继披露连接者身份。是否将目标限定为隐藏明文与事件中的真实发送者，并明确中继可见收件人和鉴权连接身份、可能关联发送关系？若仍要求向中继隐藏收件人，请先指定获批协议及威胁模型；施工者不自行引入新身份或加密格式。
2. **成员白名单语义**：礼物包裹由一次性随机公钥签名。是否允许“通过白名单身份完成 AUTH 的连接发布随机签名包裹”，读取仅限 AUTH 公钥等于外层 p 标签的连接？若要求事件签名公钥也在白名单，标准礼物包裹将无法投递。
3. **收件中继发现**：当前 NIP-17 要求只向收件人 kind 10050 声明的中继发布，无声明时不发送。任务卡只有手动连接一个或多个中继。是否在本卡加入 kind 10050 的发布/查询与无声明拒发测试？
4. **投递后即删**：白皮书 P8 要求投递后即删，卡内只明确 30 天过期。请确认本卡是否负责投递确认和删除；若负责，请明确投递成功判据（中继写入 OK、接收端解密、接收端持久化）、多设备/多中继删除与去重边界。

裁决前不把矛盾要求固化为测试，不改任务卡验收措辞，不改宪章或白皮书。批准后仍按六项验收用例先写测试，再实现；新增依赖另在同一 PR 申请版本、许可证和发布日期，批准前不安装。
