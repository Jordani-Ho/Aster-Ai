# M1-05 中继连接与端到端加密消息

- 状态：已派（DeepSeek，2026-10-16 由 Codex 改派）
- 依赖：M1-01
- 白皮书依据：§3、§4.1、参数表 P8

## 目标

两个节点（学生和老师）能通过中继互发端到端加密的消息。中继只能看到密文，看不出谁发给谁、说了什么。

## 范围

要做的：
- `app/src/core/transport/`：
  - 连接一个或多个中继，断线自动重连；
  - 发送和接收私信：采用 Nostr 的私信规范（NIP-17 私信、NIP-44 加密、NIP-59 礼物包裹）；
  - 中继鉴权（NIP-42）：只有社区成员的公钥可以读写；
  - 每条消息带过期时间（NIP-40），默认 30 天；
  - 统一的应用信封：`{ type, version, payload }`。`type` 先定义 `ping`，后续由各业务卡增加，例如 `consult.package`、`record.signed`、`ledger.event`。
- `relay/`：
  - 评估两款开源中继（例如 strfry、nostr-rs-relay），在 README 里写清选择和理由；
  - 提供本地开发用的启动方式（docker compose），开启鉴权和成员白名单，单条消息上限设为 2 MB，以容纳压缩后的照片；
  - 测试中可以用内存版的模拟中继，不依赖网络。

不做的：
- 推送提醒（M1-08）；
- 具体业务消息的格式（由各业务卡定义）。

## 已定事项（2026-10-16，PR #6 答复）

1. **隐私边界**（更正任务卡原先的写法）：按 NIP-17、NIP-59 的标准设计，外层礼物包裹的 `p` 标签就是收件人公钥，中继需要靠它投递；NIP-42 鉴权也会让中继知道连接者是谁。所以 M1 的保证是：
   - **中继看不到**：消息内容、消息里的真实发件人（外层由一次性随机密钥签名）、真实的发送时间（按 NIP-59 做时间随机化）；
   - **中继看得到**：收件人公钥、发起连接的成员公钥、连接时间。中继运营方有可能把“谁在什么时候连接”和“谁收到了信”关联起来。
   - 这一局限写进 `relay/README.md`，并要求中继**不记录连接日志**。M2 评估“每段师生关系使用单独的收信密钥”，以隐藏真实收件人。
2. **成员白名单的含义**：连接中继时，须以白名单里的成员身份完成 NIP-42 鉴权，鉴权后才能发布事件，事件本身可以由一次性密钥签名。读取 kind 1059 时，只返回外层 `p` 标签等于鉴权公钥的事件。
3. **收信中继声明（kind 10050）**：M1 不做。所有成员使用配置里的社区中继列表。M2 再接入。
4. **投递后即删**：M1 不做。礼物包裹由一次性密钥签名，收件人无法按 NIP-09 删除，只能依靠 NIP-40 的 30 天过期。白皮书参数表 P8 已同步更正。

## 注意

NIP 编号以 Nostr 官方仓库的当前版本为准，施工前先核对。**不得自造加密格式。**

## 验收用例

1. 学生节点发 `ping` 给老师节点，老师节点收到并解密，内容一致。
2. 直接查看中继里存储的事件：看不到明文，也看不到真实的发件人公钥（外层由一次性密钥签名，礼物包裹生效）；外层事件的时间戳经过随机化。
3. 非成员公钥连接中继时被拒绝读写；成员只能读到收件人是自己的事件。
4. 断开网络 30 秒后恢复，期间发送的消息在恢复后送达，且不重复。
5. 过期时间已到的消息不再被中继返回。
6. 发给第三个节点的消息，老师节点无法解密。
