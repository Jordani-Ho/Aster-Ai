# 无感上手（M1-17）

首次启动在后台生成原有BIP-39/NIP-06身份并写入现有加密库，页面只问使用角色。恢复词只在本人设备的 `recovery-words/self` 加密保存，日常界面不显示；“设置 → 换手机时用（高级）”可抄写核对或恢复。中继与文件业务备份均排除此集合；刷脸身份备份另走下述显式增强。

## 邀请

老师以原身份签名 kind27235 的邀请（NIP-98风格，非普通60秒请求凭据）。content固定 `aster.invite` v1，单个u/method/expiration/nonce标签，默认7天并可重复使用；u绑定当前部署的 `/invite/redeem`。链接用fragment封装，不放查询串，不向第三方二维码服务发送。二维码用固定 qrcode@1.5.4（MIT，2024-08-05发布）本机生成。

学生使用自己的普通NIP-98请求兑换，签名绑定本人及完整请求体；网关校验邀请者仍是现有成员、签名与期限，再原子登记请求签名人。成功后才在本机登记老师、打开原账本和保存学生角色；未发任何充值/赠送/扣费。格式、过期、非成员、错误部署或篡改统一显示邀请失效。邀请链接仅清理成功后的fragment，失败可重试；本机身份不被失败邀请替换。

## 可选刷脸

只使用当前源、平台认证器的WebAuthn发现式通行凭据与PRF，user.id为后台身份的32字节编号。注册后再登录取值，必须实际得到32字节PRF；能力标志不作成功依据。注册没输出但登录有输出可用；不支持时仅灰掉增强，取消时可重试，不影响未开启保护的基础流程。

PRF输出经WebCrypto HKDF-SHA256（固定版本用途域）派生不可导出的AES-GCM256，用随机12字节IV和绑定作者的AAD包装身份。身份密文为签名30078的独立 `aster.identity` 槽；正常业务备份仍NIP44自加密、只允许本人读取，照片仍需本机文件备份。

启用先发布身份密文、完成业务备份，成功后才把本机meta.identity改为PRF包装并用 `deviceKey='prf'` 替换旧设备CryptoKey。未拿到PRF不能启用；重新打开需要本人刷脸解锁，不把PRF输出/派生CryptoKey存入IndexedDB或业务备份。清缓存/换手机后：先用同一系统账户同步的凭据获得PRF和userHandle，无认证按完整作者及唯一身份槽读取密文，解开并复核身份；用户明确允许替换后，再本人认证恢复业务备份，最后重建本机保护。

限于浏览器/系统实际提供的PRF和同步；不承诺某型号或系统账户一定支持，不采集真人照片/人脸数据；实际验证方式由系统决定，也可能是指纹或设备PIN。跨手机需相同RP域名和相同凭据，临时Tunnel换域名无法承接旧凭据。只保持当前打开会话，重开/刷新再解锁。关闭本机保护不撤回已发出的身份密文，也不撤销系统中的旧凭据；高风险身份轮换不在本卡。手工高级恢复需要自己保管的12个词，并明确允许替换。

验证：onboarding.test.ts（签名/期限/fragment/篡改）、passkey.test.ts（实际值、注册回退、密文认证、设备保护无旁路），以及 e2e/onboarding.spec.ts 与邀请版完整九步流程。

参考：[W3C PRF说明](https://github.com/w3c/webauthn/blob/main/explainers/prf-extension.md)、[Chrome虚拟认证器接口](https://chromedevtools.github.io/devtools-protocol/tot/WebAuthn/)。
